# التمرير والافتراضية

## التمرير ينشأ من overflow

ما إن يعلن View على محور ما أنّ `overflow-x` / `overflow-y` هو `auto` أو `scroll` أو
`hidden` حتى يصير حاوية تمرير على ذلك المحور. لا حاجة لاستبداله بعنصر آخر:

```ts
View({
  style: { height: 480, overflowY: "auto" },
  children: rows,
});
```

الإيماءات والعجلة وسلسلة التمرير وشريط التمرير كلّها تُشتق من هذا الإعلان وحده: مسار
الإصابة يصعد إلى أقرب سلف قابل للتمرير، والشريط يرسمه Core من حالة التمرير التي يملكها
أصلًا، فلا تصل إطارة التمرير إلى Shell. و`hidden` يطابق CSS: لا شريط للمستخدم، لكن التمرير
البرمجي يبقى صالحًا.

**التمرير ليس افتراضية.** فـ`overflow` يجعل الصندوق يتمرّر فقط ولا يخمّن ما إذا كنت تريد
تنفيذ نافذة على البيانات. أمّا `virtual` أدناه فهو عقد صريح لا يُستنتج أبدًا من `overflow`
ولا من الأبناء المتحقّقين سلفًا.

## لماذا تعيش الافتراضية داخل المحرّك

يأتي تأخّر الذيل في القوائم الافتراضية المبنية على DOM من هذه السلسلة: يعود حدث التمرير إلى الخيط
الرئيسي، فيستدعي setState، ثمّ المقارنة، ثمّ إعادة التخطيط. وما إن ينشغل الخيط الرئيسي حتى تسقط الإطارات.

يضع pingo حساب النافذة داخل النواة: التمرير المستقرّ **لا يستدعي الغلاف إطلاقًا**. ولا يفعل الغلاف سوى
تجسيد المجال المرئي وفق نافذة التسخين التي خطّطت لها النواة؛ وإن لم تكن البيانات جاهزة رُسم عنصر نائب
واستُكمل في إطارات لاحقة.

## إعطاء View نافذة بيانات

الافتراضية خاصيّة على View لا مكوّن آخر: الصندوق المتمرّر نفسه يحمل أبناءً عاديين كما يحمل مليون صف.

```ts
View({
  style: { width: 480, height: 640, overflowY: "auto" },
  virtual: {
    axis: "y",
    itemCount: 1_000_000,
    estimatedItemSize: 32,
    getItemKey: (index: number) => `order-${index}`,
    renderItem: (index: number) =>
      View({
        style: { height: 32 },
        children: Text({ value: `الصف ${index}` }),
      }),
  },
});
```

`estimatedItemSize` مجرّد تقدير أولي. وبعد قياس الحجم الحقيقي يصحّح Core موضع المرساة عبر
شجرة مجاميع بادئة (Fenwick)، فلا يقفز الشريط.

و`axis` أحادي المحور: النافذة الواحدة تخدم `x` أو `y` لا كليهما.

ولا يزال المكوّن `VirtualList` متاحًا: فهو اختصار للقائمة الرأسيّة وينتهي إلى العقد نفسه في
النواة. أمّا للمحور الأفقي أو لـ`getItemKey` أو حين يحمل الصندوق نفسه محتوى عاديًا ونافذة معًا،
فاستعمل `virtual` على View.

## المعاملات القابلة للضبط

| حقل `virtual`            | الدور                                                      |
| ------------------------ | ---------------------------------------------------------- |
| `axis`                   | محور النافذة الوحيد، `x` أو `y` (الافتراضي `y`)            |
| `itemCount`              | إجمالي العناصر المنطقية                                    |
| `estimatedItemSize`      | التقدير الأولي للحجم، يصحّحه Core بعد القياس               |
| `getItemKey`             | معرّف ثابت للعنصر لإعادة الاستعمال عبر النوافذ             |
| `renderItem`             | يحقّق عنصرًا واحدًا، ولا يُستدعى إلّا لفهارس نافذة التسخين |
| `baseOverscanViewports`  | مدى التسخين المتماثل (بمضاعفات إطار العرض)                 |
| `velocityHorizonSeconds` | مدى إسقاط السرعة المستعمل في توقّع الاتجاه                 |
| `maximumAheadViewports`  | سقف التسخين في اتجاه واحد                                  |

يسخّن توقّع الاتجاه جهة الحركة أوّلًا عند الدفع السريع، بدل تبديد الميزانية على الجهتين بالتساوي.

## التمرير البرمجي

`scrollX` / `scrollY` خاصيّتان لـ View نفسه، مستقلّتان عن الافتراضية. وتغيّر القيمة وحده
يُصدر تعديل `ScrollTo` واحدًا:

```ts
View({ style: { height: 480, overflowY: "auto" }, scrollY: 500_000 * 32, children: rows });
```

أو عبر واجهة التحكّم المباشر على الجذر، وهي مخصّصة للإيماءات المخصّصة:

```ts
root.beginScroll(handle);
root.scrollBy(handle, 0, deltaY, elapsedMs);
root.endScroll(handle); // تتكفّل النواة بتقدير سرعة الاندفاع
```

ويأتي `handle` من ردّ نداء `ref` الخاصّ بالعنصر (`NodeHandle`).

## عجلة الفأرة ولوحة اللمس

تطابق **مسافة** التمرير بالعجلة ما يفعله المتصفّح، لكنّ منحنى النقل ينقسم بحسب مصدر الإدخال: تُطبَّق
الفروق عالية الدقّة (لوحة اللمس) بنسبة ١:١ فورًا ويبقى القصور الذاتي من تدفّق أحداث نظام التشغيل، بينما
تتراكم نقرات العجلة المنفصلة نحو هدف متحرّك يُقارَب بتباطؤ أُسّي، مقيَّدًا بحدود المحتوى بلا تجاوز، تمامًا
كما في المتصفّح.

## التداخل والتحرير

العجلة تمرّر أقرب سلف قابل للتمرير، أي أقرب View أعلن `overflow`. وإذا بدأ سحب المؤشّر فوق
نصّ قابل للتحرير فإنّ تحديد النصّ يسبق سحب التمرير؛ وهذه الأولويّة يقرّرها عمق مسار الإصابة
ولا تحتاج تدخّلًا من التطبيق.

## معيار الأداء

يشكّل قياس الأداء الآلي على تجهيزة ثابتة (مليون صفّ، عشرون ألف إطار) جزءًا من بوّابة الدمج. وحاليًا
يقلّ P95/P99 لإعادة التشغيل عن الميكروثانية، ولا يظهر نموّ ذاكرة خارج السيطرة بعد ثلاثين دقيقة من التمرير
المتواصل.

أمّا P95/P99 على الأجهزة الحقيقية وزمن استجابة الإدخال فيندرجان تحت تأهيل المنصّة وليسا شرطًا لإنهاء
العمل الهندسي. وهذا الفصل مقصود: فهو يمنع تعطيل العمل ببيانات أجهزة غير قابلة للاستنساخ، ويمنع كذلك
تقديم أرقام هندسية على أنّها وعد بخصوص الأجهزة.

يمكنك رؤية مؤشّرات الإطارات لحظيًا في [عرض التمرير داخل Playground](/ar/playground#/scroll).
