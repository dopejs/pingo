# גלילה ווירטואליזציה

## גלילה נולדת מ-overflow

ברגע ש-View מצהיר על ציר כלשהו `overflow-x` / `overflow-y` בערך `auto`, `scroll` או
`hidden`, הוא מכולת גלילה בציר הזה. אין צורך להחליף אותו באלמנט אחר:

```ts
View({
  style: { height: 480, overflowY: "auto" },
  children: rows,
});
```

מחוות, גלגלת, שרשור גלילה ופס הגלילה נגזרים כולם מההצהרה הזאת בלבד: נתיב הפגיעה עולה אל
אב הגלילה הקרוב ביותר, ואת הפס מצייר Core ממצב הגלילה שכבר בידיו, ולכן פריים של גלילה
אינו מגיע אל ה-Shell. `hidden` מתנהג כמו ב-CSS: אין פס למשתמש, אבל גלילה תוכניתית עדיין
עובדת.

**גלילה אינה וירטואליזציה.** `overflow` רק גורם לתיבה לגלול, והוא אינו מנחש אם ברצונך
לחלן את הנתונים. ה-`virtual` שלהלן הוא חוזה מפורש שלעולם אינו נגזר מ-`overflow` או מילדים
שכבר מומשו.

## למה הווירטואליזציה יושבת במנוע

השהיית הזנב של רשימות וירטואליות מבוססות DOM נובעת מהשרשרת: אירוע הגלילה חוזר לתהליכון הראשי, מפעיל
‏setState, אחריו diff ואחריו פריסה מחדש. ברגע שהתהליכון הראשי עסוק, פריימים נופלים.

‏pingo מעביר את חישוב החלון לליבה: גלילה במצב יציב **אינה קוראת למעטפת כלל**. המעטפת רק מממשת את הטווח
הנראה לפי חלון החימום שהליבה תכננה; אם הנתונים עדיין אינם מוכנים מצויר מציין מקום והוא מושלם בפריימים
מאוחרים יותר.

## לתת ל-View חלון נתונים

וירטואליזציה היא מאפיין של View ולא רכיב אחר: אותה תיבה גוללת נושאת ילדים רגילים כמו גם מיליון שורות.

```ts
View({
  style: { width: 480, height: 640, overflowY: "auto" },
  virtual: {
    axis: "y",
    itemCount: 1_000_000,
    estimatedItemSize: 32,
    getItemKey: (index: number) => `order-${index}`,
    renderItem: (index: number) =>
      View({
        style: { height: 32 },
        children: Text({ value: `שורה ${index}` }),
      }),
  },
});
```

`estimatedItemSize` הוא רק אומדן התחלתי. לאחר מדידת הגודל האמיתי, Core מתקן את מיקום העוגן
באמצעות עץ סכומי קידומת (Fenwick), והפס אינו קופץ.

`axis` הוא חד-צירי: חלון אחד משרת `x` או `y`, לא את שניהם.

הרכיב `VirtualList` עדיין קיים: הוא הקיצור לרשימה אנכית ומגיע לאותו חוזה של Core. לציר האופקי,
ל-`getItemKey`, או כשאותה תיבה צריכה לשאת גם תוכן רגיל וגם חלון, השתמשו ב-`virtual` על ה-View.

## פרמטרים לכוונון

| שדה `virtual`            | תפקיד                                             |
| ------------------------ | ------------------------------------------------- |
| `axis`                   | הציר היחיד של החלון, `x` או `y` (ברירת מחדל `y`)  |
| `itemCount`              | מספר הפריטים הלוגיים                              |
| `estimatedItemSize`      | אומדן גודל התחלתי, מתוקן על ידי Core לאחר מדידה   |
| `getItemKey`             | זהות יציבה של פריט, לשימוש חוזר בין חלונות        |
| `renderItem`             | ממש פריט בודד, נקרא רק עבור אינדקסים בחלון החימום |
| `baseOverscanViewports`  | טווח חימום סימטרי (כפולות של אזור התצוגה)         |
| `velocityHorizonSeconds` | אופק היטל המהירות, לחיזוי כיוון                   |
| `maximumAheadViewports`  | תקרת חימום בכיוון אחד                             |

חיזוי הכיוון מחמם קודם כול את כיוון התנועה בהעפה מהירה, במקום לבזבז את התקציב באופן סימטרי לשני הצדדים.

## גלילה תוכניתית

`scrollX` / `scrollY` הם מאפיינים של ה-View עצמו, ללא תלות בווירטואליזציה. רק שינוי ערך
פולט mutation יחיד מסוג `ScrollTo`:

```ts
View({ style: { height: 480, overflowY: "auto" }, scrollY: 500_000 * 32, children: rows });
```

או באמצעות ממשק המניפולציה הישירה על ה-root, המיועד למחוות מותאמות:

```ts
root.beginScroll(handle);
root.scrollBy(handle, 0, deltaY, elapsedMs);
root.endScroll(handle); // הליבה מעריכה את מהירות ההעפה
```

‏`handle` מגיע מקריאת ה-`ref` של הרכיב (`NodeHandle`).

## גלגלת ומשטח מגע

**מרחק** הגלילה בגלגלת זהה לזה של הדפדפן, אך עקומת ההעברה מתפצלת לפי מקור הקלט: דלתות ברזולוציה גבוהה
(משטח מגע) מיושמות 1:1 מיד, והאינרציה ממשיכה להגיע מזרם האירועים של מערכת ההפעלה; נקישות גלגלת בדידות
נצברות ליעד מונפש שאליו מתקרבים בהאטה מעריכית, מוגבל בקשיחות לגבולות התוכן ובלי גלישת יתר, בדיוק כמו
בדפדפן.

## קינון ועריכה

הגלגלת גוללת את אב הגלילה הקרוב ביותר, כלומר את ה-View הקרוב ביותר שהצהיר `overflow`.
כאשר גרירת מצביע מתחילה מעל טקסט הניתן לעריכה, בחירת הטקסט גוברת על גרירת הגלילה;
סדר העדיפות הזה נקבע לפי עומק נתיב הפגיעה ואינו דורש התערבות של האפליקציה.

## אמת מידה לביצועים

מדד הביצועים האוטומטי על מקבע קבוע (מיליון שורות, 20,000 פריימים) הוא חלק משער המיזוג. כיום P95/P99 של
ההרצה החוזרת נמוכים ממיקרו-שנייה, ושלושים דקות של גלילה רצופה אינן מראות גידול זיכרון בלתי מבוקר.

‏P95/P99 במכשירים אמיתיים והשהיית הקלט שייכים להסמכת פלטפורמה ואינם תנאי לסיום העבודה ההנדסית. הקו הזה
נמתח בכוונה: הוא מונע מנתוני מכשיר שאינם ניתנים לשחזור לעצור את העבודה, ומונע באותה מידה הצגת מספרים
הנדסיים כהבטחה לגבי מכשירים.

ב[הדגמת הגלילה ב-Playground](/he/playground#/scroll) אפשר לראות מדדי פריים בזמן אמת.
