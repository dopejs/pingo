# アーキテクチャ概要

## 両側の所有権

```
TSX / hooks          →  Mutation Stream  →   Scene / Layout / Paint
（TypeScript Shell）      バイナリ、バッチ        （Rust Core、wasm）
                                                    ↓
Canvas2D 再生器      ←   DisplayList      ←    Picture
```

**Shell はコンポーネントツリーを所有し、Core は Scene を所有する。両者は可変オブジェクトを共有しない。**
すべての境界を越える通信はバージョン管理されたバイナリストリームである。リトルエンディアン、4 バイトアライメント、命令化されており、受信側はメモリアクセス前に opcode、長さ、アライメント、ID、算術検証を完了する。不正な入力は原子的に拒否され、部分適用はされない。

この境界はパフォーマンス最適化ではなく、正当性の境界である。バイトが通常は本プロジェクト自身のエンコーダー由来であっても、デコーダーは信頼できない入力として扱い、fuzz カバレッジを持つ。

## デュアルクロック

UI クロック（メインスレッド）とレンダリングクロック（Worker）は相互に独立している。

- メインスレッドは入力を収集し、コンポーネントツリーを走らせ、Mutation フレームをコミットする。
- Worker はスクロール物理、アニメーション、レイアウト、合成を駆動する。

**スクロールの定常状態は Shell を呼び出さない。** 欠落したデータはプレースホルダーで描画され、後続フレームで補完される。そのためメインスレッドが業務コードで 200ms ブロックされても、スクロールとアニメーションは継続する。このシナリオは自動故障注入テストで守られている。

## フォールバックチェーン

能力検出は順序に従って転送パスを選択し、3 段階の機能等価を実現する。

1. **SharedArrayBuffer** —— クロスオリジン分離（COOP/COEP）が必要
2. **postMessage** —— SAB がない場合
3. **メインスレッド Canvas2D** —— Worker / OffscreenCanvas がない場合

```ts
const root = await createHostedCanvasRoot(canvas, {
  transport: { preference: "sab" }, // 任意の優先設定、満たされない場合でもフォールバックする
});
console.log(root.mode); // "sab" | "post-message" | "main-thread"
```

本サイトの [Playground](/playground) が生きた例である。GitHub Pages は COOP/COEP レスポンスヘッダーを配信できないため、オンラインでは postMessage パスで動作し、ページ上部の transport マーカーがそのまま表示される。

## 無効化モデル

**prop の意味論が無効化ドメインを決定する**。呼び出し側は手動でダーティフラグを立てず、`forceUpdate` の逃げ道も存在しない。

各プロパティは単一ソースのスキーマで、レイアウト・描画・ヒット・意味論のどれに影響するかを宣言する。`opacity` を変更しても再レイアウトは発生しない。`width` を変更すれば発生する。ダーティビットマップはドメインごとに維持され、`onFrame` は各ドメインのダーティノード数を公開する。

この選択は「積極的な最狭無効化 + プロパティテストによる下支え」である。差分レンダリング結果は全量レンダリングとピクセル単位で一致しなければならず、差分テストは反例を最小の失敗ケースに収束させる。

## Scene 表現

Core 内の Scene は SoA（構造体配列から配列の構造体へ）である。

- ノード ID は**世代**を含み、スロット再利用で期限切れ ID が再び有効になることはない。
- commit 後は**トポロジカル順序**を維持する。親ノードは常に子ノードより前に並ぶ。
- 構造編集は mutation ごとではなく、commit ごとに 1 回コンパクト化される。
- レイアウト結果はダブルバッファ SoA でバッチ比較され、ホットパス上にノードごとのクロージャやリスナー割り当てはない。

## バックエンドのプラグイン化

Core はフラットなバイナリ DisplayList を出力し、バックエンドは再生器にすぎない。Canvas2D バックエンドは割り当てを抑えた typed-array ループである。**描画ごとに wasm→JS を呼び出すことは許容可能なレンダリングパスではない**。

同じ DisplayList は分離された wgpu プロトタイプにも供給され、両者の出力はピクセル差分が取られる。
WebGPU を採用するかどうかはデータに基づく決定である。[ADR-0006](https://github.com/dopejs/pingo/blob/main/docs/adr/0006-webgpu-backend-decision.md) を参照。

## 決定性

時間、乱数源、入力ストリームは注入または再生可能であり、Core の出力はスレッドスケジューリング順序に依存しない。
`DOPR` アーカイブは Mutation と Input ストリームを元の順序で記録し、ブラウザから切り離して headless 環境で決定的に再生できる。これによりオンラインの問題をローカルで再現でき、機密性の高い編集ストリームは明示的に記録をスキップする。

## コンポーネントとスタイル

このカーネルの上に、作者向けの 3 層の API がある。

- **基礎コンポーネント** —— View/Text/Image、Input/TextArea、SVG/Path などのエンジンレベル要素。[基礎コンポーネント](/guide/elements)を参照。
- **スタイル** —— Shell 側で解析されるバージョン管理された CSS subset（対応表は[こちら](/style-support)）、およびビルド時の
  [SCSS/Less パイプライン](/guide/scss-less)。Core は正規化された型付き値のみを消費し、CSS テキストを解析しない。
- **UI コンポーネントライブラリ** —— `@dopejs/pingo-ui`。shadcn/ui と整合する完成品コンポーネントで、すべて canvas にレンダリングされる。
  [コンポーネントドキュメント](/components)を参照。
