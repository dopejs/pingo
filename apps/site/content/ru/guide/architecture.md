# Обзор архитектуры

## Владение с обеих сторон

```
TSX / хуки          →   Поток мутаций    →   Scene / Layout / Paint
（оболочка TypeScript）      бинарный, пакетный       （ядро Rust，wasm）
                                                    ↓
Проигрыватель Canvas2D  ←   DisplayList      ←    Picture
```

**Оболочка владеет деревом компонентов, ядро владеет Scene. Обе стороны не разделяют изменяемых объектов.**
Все межграничные коммуникации — это версионированные бинарные потоки: little-endian, выравнивание по четырём байтам, инструкционные; принимающая сторона до обращения к памяти выполняет проверку
opcode, длины, выравнивания, идентификатора и арифметики. Повреждённый ввод атомарно отклоняется, а не применяется частично.

Эта граница — не оптимизация производительности, а граница корректности: даже если байты обычно приходят от собственного кодировщика проекта, декодер относится к ним как к недоверенному
вводу, и это покрыто фаззингом.

## Двойные часы

Часы пользовательского интерфейса (главный поток) и часы рендеринга (Worker) независимы друг от друга:

- Главный поток собирает ввод, обрабатывает дерево компонентов, отправляет кадры мутаций.
- Worker управляет физикой прокрутки, анимацией, раскладкой и композитингом.

**Устойчивое состояние прокрутки не вызывает оболочку.** Отсутствующие данные рендерятся запасными вариантами и достраиваются в последующих кадрах. Поэтому, когда бизнес-код блокирует главный поток на 200 мс,
прокрутка и анимация остаются непрерывными — этот сценарий защищён тестом с автоматическим внедрением сбоев.

## Цепочка деградации

Обнаружение возможностей последовательно выбирает путь передачи, три уровня функционально эквивалентны:

1. **SharedArrayBuffer** —— требуется кросс-доменная изоляция (COOP/COEP)
2. **postMessage** —— при отсутствии SAB
3. **Canvas2D в главном потоке** —— при отсутствии Worker / OffscreenCanvas

```ts
const root = await createHostedCanvasRoot(canvas, {
  transport: { preference: "sab" }, // необязательное предпочтение, при невыполнении всё равно деградирует
});
console.log(root.mode); // "sab" | "post-message" | "main-thread"
```

[Playground](/playground) на этом сайте — живой пример: GitHub Pages не может отправлять заголовки COOP/COEP,
поэтому в проде он работает по пути postMessage, и маркер transport вверху страницы честно это показывает.

## Модель инвалидации

**Семантика prop определяет область инвалидации**; вызывающая сторона не помечает вручную «грязные» области, и нет спасательного люка `forceUpdate`.

Каждое свойство в единой схеме объявляет, влияет ли оно на раскладку, отрисовку, попадание или семантику. Изменение `opacity` не вызовет повторной раскладки;
изменение `width` — вызовет. Карта грязных битов ведётся по областям, `onFrame` показывает количество грязных узлов по каждой области.

Этот выбор — «агрессивно узкая инвалидация + страховка property-тестами»: результат инкрементального рендеринга должен попиксельно совпадать с полным рендерингом,
дифференциальные тесты сводят контрпример к минимальному падающему случаю.

## Представление Scene

Scene внутри ядра — это SoA (структура массивов вместо массива структур):

- Идентификатор узла включает **поколение**, повторное использование слота не позволяет устаревшему идентификатору снова стать действительным.
- После commit сохраняется **топологический порядок**: родительский узел всегда стоит перед дочерним.
- Структурные правки компактифицируются один раз за commit, а не один раз за мутацию.
- Результаты раскладки сравниваются пакетно с использованием двойной буферизации SoA, на горячем пути нет выделения замыканий или слушателей на каждый узел.

## Подключаемые бэкенды

Ядро выдаёт плоский бинарный DisplayList, бэкенд — это лишь проигрыватель. Бэкенд Canvas2D — это скупой на выделения
цикл с typed-array — **вызов wasm→JS при каждой отрисовке не является приемлемым путём рендеринга**.

Тот же DisplayList подаётся и в изолированный прототип wgpu, выходные данные обоих сравниваются попиксельно.
Решение о внедрении WebGPU принимается на основе данных, см. [ADR-0006](https://github.com/dopejs/pingo/blob/main/docs/adr/0006-webgpu-backend-decision.md).

## Детерминированность

Время, источник случайности и поток ввода можно внедрять или воспроизводить, вывод ядра не зависит от порядка планирования потоков.
Архив `DOPR` записывает потоки мутаций и ввода в исходном порядке и может детерминированно воспроизводиться вне браузера в headless-окружении —
благодаря этому проблемы из прода можно воспроизвести локально, чувствительные потоки правок явно пропускаются при записи.

## Компоненты и стили

Поверх этого ядра расположены три уровня API, ориентированных на авторов:

- **Базовые компоненты** —— элементы уровня движка: View/Text/Image, Input/TextArea, SVG/Path и другие, см. [базовые компоненты](/guide/elements).
- **Стили** —— версионированное подмножество CSS, разбираемое на стороне оболочки (таблица поддержки [здесь](/style-support)), а также
  [конвейер SCSS/Less](/guide/scss-less) на этапе сборки; ядро потребляет только нормализованные типизированные значения и не разбирает CSS-текст.
- **Библиотека UI-компонентов** —— `@dopejs/pingo-ui`, готовые компоненты, выровненные с shadcn/ui, все рендерятся в canvas,
  см. [документацию компонентов](/components).
