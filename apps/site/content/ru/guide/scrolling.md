# Прокрутка и виртуализация

## Прокрутка рождается из overflow

Как только View объявляет по оси `overflow-x` / `overflow-y` со значением `auto`,
`scroll` или `hidden`, он становится контейнером прокрутки по этой оси. Менять его на
другой элемент не нужно:

```ts
View({
  style: { height: 480, overflowY: "auto" },
  children: rows,
});
```

Жесты, колесо, цепочка прокрутки и полоса выводятся из одного этого объявления: путь
попадания поднимается к ближайшему прокручиваемому предку, а полосу рисует Core из
состояния прокрутки, которым он и так владеет, поэтому кадр прокрутки не доходит до
Shell. `hidden` ведёт себя как в CSS: полосы для пользователя нет, программная прокрутка
работает.

**Прокрутка — не виртуализация.** `overflow` лишь делает бокс прокручиваемым и не гадает,
нужно ли окно по данным. Идущий ниже `virtual` — явный контракт, который никогда не
выводится из `overflow` или из уже материализованных детей.

## Почему виртуализация живёт в движке

Хвостовые задержки виртуальных списков на DOM берутся из цепочки: событие прокрутки возвращается в
главный поток, вызывает setState, затем diff, затем переразметку. Как только главный поток занят, кадры
теряются.

pingo переносит расчёт окна в ядро: установившаяся прокрутка **никогда не вызывает оболочку**. Оболочка
лишь материализует видимый диапазон по окну прогрева, которое спланировало ядро; если данные ещё не
готовы, рисуется заглушка, а на следующих кадрах она дополняется.

## Дать View окно данных

Виртуализация — свойство View, а не другой компонент: один и тот же прокручиваемый бокс несёт и обычных детей, и миллион строк.

```ts
View({
  style: { width: 480, height: 640, overflowY: "auto" },
  virtual: {
    axis: "y",
    itemCount: 1_000_000,
    estimatedItemSize: 32,
    getItemKey: (index: number) => `order-${index}`,
    renderItem: (index: number) =>
      View({
        style: { height: 32 },
        children: Text({ value: `Строка ${index}` }),
      }),
  },
});
```

`estimatedItemSize` — лишь начальная оценка. После измерения реального размера Core
корректирует положение якоря через дерево префиксных сумм (Fenwick), и полоса не прыгает.

`axis` односевая: одно окно обслуживает `x` либо `y`, но не оба сразу.

Компонент `VirtualList` никуда не делся: это сокращение для вертикального списка, приводящее к
тому же контракту Core. Для горизонтальной оси, для `getItemKey` или когда одна и та же коробка
должна нести и обычное содержимое, и окно, используйте `virtual` на View.

## Настраиваемые параметры

| Поле `virtual`           | Роль                                                                 |
| ------------------------ | -------------------------------------------------------------------- |
| `axis`                   | Единственная ось окна, `x` или `y` (по умолчанию `y`)                |
| `itemCount`              | Общее число логических элементов                                     |
| `estimatedItemSize`      | Начальная оценка размера, после измерения уточняется Core            |
| `getItemKey`             | Стабильный идентификатор элемента для переиспользования между окнами |
| `renderItem`             | Материализует элемент, вызывается только для индексов окна           |
| `baseOverscanViewports`  | Симметричный диапазон прогрева (в размерах вьюпорта)                 |
| `velocityHorizonSeconds` | Горизонт проекции скорости для предсказания направления              |
| `maximumAheadViewports`  | Предел прогрева в одну сторону                                       |

Предсказание направления при быстром броске прогревает прежде всего сторону движения, а не тратит
бюджет симметрично на обе.

## Программная прокрутка

`scrollX` / `scrollY` — свойства самого View, независимые от виртуализации. Только
изменение значения порождает одну мутацию `ScrollTo`:

```ts
View({ style: { height: 480, overflowY: "auto" }, scrollY: 500_000 * 32, children: rows });
```

Либо API прямого управления на root — для собственных жестов:

```ts
root.beginScroll(handle);
root.scrollBy(handle, 0, deltaY, elapsedMs);
root.endScroll(handle); // оценку скорости броска берёт на себя ядро
```

`handle` приходит из колбэка `ref` элемента (`NodeHandle`).

## Колесо и трекпад

**Расстояние** прокрутки колесом совпадает с браузерным, но кривая передачи разделяется по источнику
ввода: дельты высокой точности (трекпад) применяются 1:1 сразу, а инерцию по-прежнему поставляет поток
событий операционной системы; дискретные щелчки колеса накапливаются в анимационную цель, к которой
движение идёт по экспоненциальному замедлению, жёстко ограничивается границами содержимого и не даёт
перепрокрутки — ровно как в браузере.

## Вложенность и редактирование

Колесо прокручивает ближайшего прокручиваемого предка — то есть ближайший View с
объявленным `overflow`. Если перетаскивание указателем началось на редактируемом тексте,
выделение текста имеет приоритет над прокруткой. Этот приоритет определяется глубиной в
пути попадания, вмешательство приложения не требуется.

## Критерий производительности

Автоматический бенчмарк на фиксированной фикстуре (миллион строк, 20 000 кадров) входит в набор
проверок при слиянии. Сейчас P95/P99 воспроизведения меньше микросекунды, а тридцать минут непрерывной
прокрутки не показывают неконтролируемого роста памяти.

P95/P99 на реальных устройствах и задержка ввода относятся к квалификации платформы и не являются
условием завершения инженерных работ. Эта граница проведена намеренно: она не даёт невоспроизводимым
данным с устройств блокировать работу и в то же время не позволяет выдавать инженерные цифры за
обещание для устройств.

В [демонстрации прокрутки в Playground](/ru/playground#/scroll) видны покадровые метрики в реальном времени.
