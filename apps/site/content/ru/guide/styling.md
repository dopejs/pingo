# Стили

Стили pingo — это **версионированный CSS subset** (сейчас 1.6.0): CSS-текст разбирается и вычисляется на стороне Shell,
Core потребляет только нормализованные типизированные значения — CSS-текст и сопоставление селекторов никогда не попадают в Core.
Полная таблица поддерживаемых свойств приведена в [CSS subset поддержка](/guide/style-support), на этой странице описываются использование и границы.

## Создание и регистрация таблиц стилей

Используйте `createStyleSheet` для компиляции CSS-текста (при некорректном вводе выбрасывается `StyleSheetCompileError`),
регистрируйте при создании root:

```ts
import { createElement, createHostedCanvasRoot, createStyleSheet } from "@dopejs/pingo";

const sheet = createStyleSheet(
  `
  .card {
    background-color: #ffffff;
    border-radius: 8px;
    padding: 16px;
  }
  `,
  { sourceName: "app.css" },
);

const root = await createHostedCanvasRoot(canvas, { styleSheets: [sheet] });

root.render(
  createElement("container", {
    className: "card",
    width: 320,
    children: createElement("text", { value: "你好", fontSize: 14 }),
  }),
);
```

Если не хотите обрабатывать исключения, используйте `compileStyleSheet`: он не выбрасывает исключений для авторского ввода и возвращает стабильные
diagnostics. Таблицу стилей также можно записать в типобезопасной объектной форме (`PingoStyleSheetObject`), где ключи — это
селекторы классов с опциональной ведущей точкой, а значения — `PingoStyle`:

```ts
const sheet = createStyleSheet({
  "card": { backgroundColor: "#ffffffff", borderRadius: 8, padding: 16 },
  "card:hover": { backgroundColor: "#f5f5f5ff" },
});
```

Элементы привязывают классы через prop `className` (несколько имён классов, разделённых пробелами ASCII), а инлайн-объявления
записывают через prop `style` (`PingoStyle`, разбирается Shell перед передачей в Core).

## Селекторы и каскад

Subset поддерживает только **селекторы классов на одном узле** и четыре псевдокласса интерактивных состояний:

- Одиночный класс `.card`; составной класс `.pui-card.pui-dark` (срабатывает, только если узел имеет все классы одновременно).
- Состояния `:hover`, `:active`, `:focus`, `:focus-visible`, могут комбинироваться с классами, например `.btn:hover`.

Не поддерживаются: селекторы элементов, комбинаторы потомков/дочерних элементов и т.п., `@media` / `@supports` / `@keyframes`,
`var()` / `calc()`. Единицы длины — только `px` и `%` (`em` / `rem` / `vw` / `vh` будут отклонены);
цвета записываются в hex или `rgb()` / `rgba()` / `hsl()` / `hsla()` (принимаются оба синтаксиса — старый и новый),
ключевые слова цветов (например `red`) не поддерживаются.

Правила каскада изоморфны CSS, но проще:

1. **Приоритет (specificity) = количество классов + количество состояний**. `.pui-card.pui-dark` (2) сильнее `.card` (1).
2. **При одинаковом приоритете действует source order**: применяются таблицы стилей, зарегистрированные позже, и правила, расположенные позже в одной таблице.
3. **Инлайн prop `style` переопределяет все правила таблиц стилей**; прямые props элемента (такие как `width`,
   `backgroundColor`) имеют наивысший приоритет, сильнее `style`.

Обратите внимание на следствие из пункта 2: основанием для переопределения является **порядок регистрации таблиц стилей**,
и он не связан с порядком имён классов в строке `className`.

## Наследование и границы вычисленных стилей

Наследуется лишь небольшой набор свойств: `color`, `visibility`, `font-family` / `font-size` / `font-weight` /
`font-style`, `line-height`, `text-align`, `white-space`, `overflow-wrap`,
`pointer-events`, `cursor`. Все остальные свойства (включая все свойства макета) у каждого узла начинаются с начального значения,
не указаны — значит отсутствуют — поведения «унаследовать ширину от родителя» не существует.

Каждое свойство в единой схеме источников объявляет свою область инвалидации (макет/отрисовка/попадание/семантика). Изменение `opacity`
не вызывает перекомпоновку, изменение `width` — вызывает; это тот же механизм, что и модель инвалидации в [архитектуре](/guide/architecture).

### Свойства в объявлениях интерактивных состояний ограничены

В правилах состояний (например `.btn:hover`) разрешены только свойства отрисовки: `background-color`, `color`,
`opacity`, `border-*-color` для каждой стороны, `border-radius`, `box-shadow`, `visibility`,
`transform` / `transform-origin`, `pointer-events`, `cursor`. Свойства макета в правилах состояний
отклоняются на этапе компиляции — переключение состояния не может вызывать изменение макета.

## Основные отличия от CSS

Subset сознательно не обеспечивает полную совместимость с CSS, ключевые отличия (полный список см. в [CSS subset поддержка](/guide/style-support)):

- Содержащий блок для `position: absolute` — это **родительский узел**, а не ближайший позиционированный предок;
  `position: relative` отсутствует, визуальное смещение выполняется через `transform`.
- Нет `flex-wrap`: flex-контейнер однострочный, переполнение по главной оси обрезается или прокручивается.
- У flex item нет автоматического минимального размера, он может быть сжат до 0 (эквивалентно записи `min-width: 0` в браузере);
  `min-width: auto` / `min-height: auto` просто не компилируются.
- Если размер по главной оси не определён, проценты разрешаются в `0`, а не в `auto`, как в CSS.
- `box-shadow` поддерживает только внешние тени, максимум 4 слоя на узел, `inset` отклоняется.
- `z-index` лишь стабильно переупорядочивает элементы среди соседей, stacking context отсутствует.

## Темы и соглашения по переопределению в pingo-ui

Скин библиотеки компонентов `@dopejs/pingo-ui` — это таблица стилей, скомпилированная описанными выше механизмами:

```ts
import { createHostedCanvasRoot, createStyleSheet } from "@dopejs/pingo";
import { createPingoUiStyleSheet } from "@dopejs/pingo-ui";

const myOverrides = createStyleSheet(`
  .pui-button { border-radius: 4px; }
`);

const root = await createHostedCanvasRoot(canvas, {
  styleSheets: [createPingoUiStyleSheet(), myOverrides], // Порядок менять нельзя
});
```

- **`createPingoUiStyleSheet()` создаёт для каждого root отдельную независимую неизменяемую sheet**.
- **Пользовательские sheet должны регистрироваться после sheet pingo-ui**: при одинаковом приоритете действует source order,
  написанное позже применяется. Prop `className` компонента добавляется после собственных имён классов компонента
  (например `pui-input pui-input--disabled mine`), но возможность переопределения зависит только от указанного выше порядка регистрации.
- Чтобы повысить приоритет переопределения, используйте составной класс для увеличения specificity (например `.pui-button.mine`), а не
  полагайтесь на позицию записи.

### Светлая и тёмная темы

```ts
import { setTheme, useTheme } from "@dopejs/pingo-ui";

setTheme("dark"); // Все подписанные компоненты автоматически перерисовываются
useTheme(); // Читает и подписывается внутри render компонента
```

Тема — это signal уровня модуля: в render компонента `useTheme()` автоматически подписывается, а `setTheme` запускает
перерисовку всех подписанных компонентов. Тёмная тема реализована через compound class — в тёмной теме компонент получает
класс-маркер `pui-dark`, и составные правила `.pui-x.pui-dark` в скине срабатывают (например `.pui-card.pui-dark`).

**Кастомизация бренда — это поведение на этапе сборки**: для нового preset используйте
`@use "@dopejs/pingo-ui/styles/tokens" with ($primary: ...)` для переопределения token, затем перекомпилируйте
скин компонентов через Vite-плагин `@dopejs/pingo-style-preprocess` — смена фирменного цвета = повторная
сборка, во время выполнения это невозможно. Цвета в значениях token также могут быть записаны только в hex или
`rgb()` / `rgba()` / `hsl()` / `hsla()`. О конвейере SCSS/Less см.
[руководство по SCSS / Less](/guide/scss-less).
