# E11 设计门：视口裁剪

- 状态：Proposed
- 日期：2026-08-26
- 关联：[`design.md`](design.md) §2.1 高刷目标、ADR-0008 immutable Picture
- 定位：**回放侧不该为看不见的东西付派发成本。**

## 1. 现状：付了 4,700 条指令，只看得见 120 条

首次实测（本机 Apple M4 Pro，400 行非虚拟化列表，Core 自驱滚动 60 帧，
`main-thread.ts` 补上 dynamic 路径计时之后）：

| 阶段        |     p50 |     p95 |
| ----------- | ------: | ------: |
| `coreMs`    | 0.745ms | 0.920ms |
| `replayMs`  | 1.035ms | 1.450ms |
| commands/帧 |   4,813 |         |

4,813 条指令 1.035ms，**每条约 215ns**。视口 480px、行高 48px，可见的是 10 行、
约 120 条指令——**其余约 4,700 条被 Canvas2D 裁掉，却仍然逐条付了派发成本，并且
占了这 1.035ms 的绝大部分**。

同一帧的 `dirtyPaintNodes = 1`、`layoutVisitedNodes = 0`：Core 已经准确知道没有
东西变化，回放照样把整棵树跑了一遍。

按 [`design.md`](design.md) §2.1 新增的 120Hz 预算（8.33ms）折算，这约 0.9ms 是
**一帧的 11%**，而这还是一个每行只有两个子节点、无图片无视频的简单场景。

## 2. 为什么不能在 Core 生成时裁剪

`pingo-paint/src/engine.rs:746` 把子 picture 的 `DrawPicture` 引用 push 进**父
picture 的 payload**；`:826` 只向顶层 DisplayList 发一条根 `DrawPicture`。所以：

```
DisplayList (32 bytes)
  └─ DrawPicture(root)
       └─ payload: DrawPicture(row 0), DrawPicture(row 1), … ×400
            └─ payload: 各行子节点的绘制指令
```

子引用**躺在不可变的 picture 字节里**。按可见窗口裁剪意味着每个滚动帧重建这些
payload，而"纯滚动帧不重建未变化子树"正是 M9-B 的出口条件。**这条路与已交付的
不变量直接冲突，不予采纳。**

## 3. 候选方案

裁剪只能发生在展开 `DrawPicture` 的那一刻，判据是"这个 picture 的包围盒与当前
裁剪框是否相交"。分歧在**包围盒从哪来**。

### 方案 A：包围盒进 ABI（Core 提供）

`DefinePicture` 增加包围盒字段，回放展开前先做相交测试。

- **优点**：Core 在布局阶段本就精确知道每个子树的几何，不需要任何人重算；所有
  后端（Canvas2D、headless oracle、未来 wgpu）共享同一份判据，不存在实现分歧；
  与 §2.1 高刷目标下的 GPU 路线叠加（GPU 也不该为不可见内容付调用成本）。
- **代价**：这是版本化二进制契约变更，按 AGENTS.md 需要：ABI 版本号、生成定义、
  golden 字节、TS↔Rust 往返、畸形输入测试、fuzz 覆盖，且两侧实现原子更新。

### 方案 B：后端自算包围盒（无 ABI 变更）

后端在 `DefinePicture` 校验遍历 payload 时顺带算出包围盒并缓存。

- **优点**：不动 ABI；校验本来就要走一遍这些字节，边际成本低；完全在后端内部，
  可独立回滚。
- **代价**：每个后端各算一次，是重复实现也是分歧风险；包围盒要正确处理 picture
  内部的 `Transform` / `ClipRect`，算错就是**丢内容**（比慢严重得多）；Core 明明
  已经知道答案，却让后端重新推导——与"Core 拥有几何"的架构取向相悖。

### 方案 C：只裁剪滚动容器（Core 改变 picture 组合粒度）

让可滚动容器的子节点在顶层 DisplayList 直接扁平引用，在那一层裁剪。

- **优点**：无 ABI 变更；顶层列表从 1 条变成"可见行数"条，仍然极小。
- **代价**：只解决滚动容器，深层嵌套树不受益；改变 picture 组合策略，需要重新
  论证 M9 的复用不变量；本质是把虚拟化的一部分硬编码进 Core。

## 4. 待决问题（进入实现前必须回答）

1. **选 A / B / C。** 我的倾向是 **A**，理由是几何归 Core 是既有架构取向，且它是
   唯一一个让未来 GPU 后端免费受益的方案；但它的代价是一次完整 ABI 变更流程。
2. **裁剪的正确性 oracle。** 必须有"裁剪路径 ↔ 不裁剪路径逐像素相同"的差分，且
   在裁剪判据错误时**必然失败**——丢内容比慢严重，这条不能只靠帧时验证。
3. **收益的度量口径。** 收益应以**每帧展开的 picture 数与指令数**计量（跨设备
   恒定），而非毫秒；毫秒作为佐证记录，不作为门禁阈值。
4. **与栅格缓存的关系。** 裁剪之后 `rasterFrame` 的命中条件是否改变，需要一并
   评估，避免修好一层又让另一层失效。

## 5. 失败模式与回滚

| 失败模式                | 判据                           | 处置                       |
| ----------------------- | ------------------------------ | -------------------------- |
| 包围盒算小，内容被丢    | 裁剪↔不裁剪逐像素差分出现差异  | 立即回滚开关，不放宽容差   |
| 变换/裁剪嵌套下判据失效 | 属性测试在随机嵌套下失败       | 停止合入，先补齐几何折叠   |
| 收益低于预估            | 展开数下降但指令数未按比例下降 | 记录实测，重新评估是否值得 |

裁剪必须由优化级开关控制，关闭后回到当前的全量展开路径，且公开 API、Scene、
Mutation Stream 与 ABI 语义不受影响。

## 6. 本文不做的事

不实现任何方案；不改 ABI；不改 picture 组合策略。本文只固定问题、排除一条已被
证伪的路径（§2）、并把三个候选的代价摊开供评审。
