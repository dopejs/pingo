# E15 设计门：文档编辑器（tiptap / 飞书文档形态）

- 状态：Adopted（2026-09-01 实现，P0–P5 与 E 全部落地）
- 日期：2026-09-01（2026-09-01 重写：上一版按「Core 缺哪几个功能」罗列，构不成一个
  文档编辑器）
- 关联：[`AGENTS.md`](../AGENTS.md) scope 排除项与「Editable text is a Core
  subsystem」不变量、[`design.md`](design.md) 编辑子系统与 ADR-0003 虚拟化数据契约、
  [`m10-capability-decisions.md`](m10-capability-decisions.md) §重新评审条件
- 定位：**这是一个文档模型问题，不是一个文本样式问题。**

## 1. 验收行为

不用特性名词，用必须成立的行为定义目标。下面每一条都要能写成自动断言：

1. 段落中间三个字加粗，其余不变。
2. 输入 `**粗体**`，收尾定界符提交时标记消失、范围加粗。
3. 段首输入 `## ` 变成二级标题，标记消失。
4. 回车分块；空列表项上回车跳出列表而不是再加一项。
5. Tab 缩进列表项，Shift-Tab 反缩进；列表可嵌套。
6. 点选一张图片按 Delete 删掉它（选中的是块，不是文本）。
7. caret 能停在两个相邻图片之间并从那里开始输入。
8. 从网页粘贴保留标题/列表/加粗结构；复制出去能得到 HTML 与 markdown。
9. Ctrl+Z 撤销一次输入突发或一次自动格式化，不是一个字符。
10. 五千块的文档滚动不掉帧，编辑不随文档长度变慢。
11. 中文输入法在 mark 边界与块边界上组合正确。

第 4、5、6、7 条是上一版**结构上做不到**的：它把文档定义成扁平块序列，且选区只有文本
偏移。本文的重写就是为了这四条。

## 3. 关键决策：文档模型放在哪一侧

这是整篇的核心，其余各节都是它的推论。

### 3.1 三个方案

**方案 I —— 整个文档模型在 Core。** Core 拥有树、schema、命令、选区、undo。
优点是单一真相源。缺点是 schema 与命令天然是应用可配置的，放进 Rust 就要发明一套序列化
的 schema 描述语言；而且 **Scene 已经是一棵由 Shell 拥有的树**，Core 再拥有第二棵，
两棵树的对齐会变成一个持续的正确性负担。

**方案 II —— 整个文档模型在 Shell。** 像 ProseMirror 那样，Shell 拥有树、映射、选区，
Core 退回到「一个块一个纯文本输入框」。
这**违反不变量**：跨块选区、跨块 undo、跨块 IME 会全部落到 Shell，而
`AGENTS.md` 明确写着 caret、选区、IME、剪贴板、undo/redo 归引擎。它还会让每次按键都
必须往返 Shell。

**方案 III（采纳）—— 按职责切，不按层切。**

### 3.2 切法

关键观察：**ProseMirror 的核心技巧是用一个扁平整数位置空间表达一棵树。** 树结构与位置
空间本来就是两件事，可以分给两侧：

| 归属      | 内容                                                                                          |
| --------- | --------------------------------------------------------------------------------------------- |
| **Shell** | 文档树、schema、命令、输入规则、序列化（HTML/markdown）、粘贴规整                             |
| **Core**  | 扁平位置空间、每块的文本与 styled runs、shaping、caret 几何、三种选区、IME、undo 栈、位置映射 |

Shell 每次提交时向 Core 声明一份**投影**：有序的块列表，每块给出稳定 key、文本、run 表，
以及「这块是不是原子」。Core 不知道列表为什么嵌套，也不需要知道——它只在这个序列上维护
位置、选区、组合与撤销。

这样切的三个理由：

1. **不新增第二棵树。** 树的增删改本来就是 Shell 每天在做的事（组件树 → Mutation
   Stream → Scene），Core 复用结果而不是复制结构。
2. **不违反不变量。** caret、选区、IME、undo 仍然全部在 Core，而且是跨块原子的——因为
   它们建立在 Core 自己的位置空间上。
3. **schema 与命令留在能表达它们的语言里。** 「Tab 意味着什么」是应用语义，属于 Shell。

### 3.3 位置空间

Core 的文档坐标是 `(block_key, utf16_offset)`，块序列由 Shell 声明。Core 额外维护一个
线性化位置，用于映射与跨块比较。

`block_key` 由 Shell 分配且在块的生命周期内稳定（分裂产生新 key，合并保留前者的 key）。
Core 不解释 key，只用它做同一性判断——这与 `getItemKey` 在虚拟列表里的角色相同。

## 4. 三种选区

`Selection` 从 `{ anchor, focus }` 扩展为三态：

- **Text**：`(block_key, utf16_offset)` 的一对锚点，可跨块。
- **Node**：一个 `block_key`，或一个行内原子的 id。整块作为对象被选中，Delete 删除它。
- **Gap**：两个块之间的位置，caret 在此可见并可开始输入。

Core 需要知道哪些位置不可进入（原子块、行内原子），才能让方向键正确跨过。这由 Shell 在
投影里声明 `atomic: bool`，而不是 Core 去猜。

**行内原子对象**（mention、emoji、行内图片）由此顺带成立：它在块的文本里占一个哨兵码位，
run 表把它标成原子，caret 整体跨过它。上一版把它列为排除项，是因为当时没有原子的概念；
在本设计里它是同一个机制的退化情形。

## 5. 位置映射

每个 `EditTransaction` 带一个映射（旧位置 → 新位置）。这是**全仓库唯一一份**范围变换
逻辑，Shell 消费它来搬运自己持有的东西：链接 href 的范围、评论锚点、协同的远端光标。

上一版把「范围变换会有两份、两份不一致就是链接错位」列成未决项。本设计里它不是未决项，
而是被消除了：Core 产出映射，Shell 应用映射，没有第二份实现。

链接的 href 因此留在 Shell 的文档树上（它不影响绘制，绘制需要的颜色与下划线在
`style_id` 里），Shell 用映射维护它的范围。

## 6. 结构编辑的往返

回车分块、Tab 缩进、块首退格合并会改变树，而树在 Shell。流程复用虚拟列表已经验证过的
形状（`engine.rs:2433` 的注释：请求在渲染之后发出，绝不在 Core 帧循环里调用 Shell）：

```
按键 → Core 识别结构意图 → 乐观地在位置空间上预演，caret 立即就位
     → 帧后发出结构请求 → Shell 按 schema 决定实际结构 → 下一帧提交新投影
     → Core 用 revision 校正（Shell 的结果与预演不同时以 Shell 为准）
```

一帧延迟只发生在改变结构的按键上，不发生在普通输入上。**乐观预演是必需的**：没有它，
回车之后的 caret 会闪一帧，那是编辑器最刺眼的缺陷之一。

schema 决定权在 Shell 这一侧，正是为了让「空列表项上回车跳出列表」这种规则可配置。

## 7. Shell 侧：`@dopejs/pingo-editor`

- **schema**：节点类型、允许的嵌套、块属性（标题层级、列表有序性、代码块语言）。
- **命令**：`toggleMark`、`splitBlock`、`liftListItem`、`setBlockType`……每个命令产出
  一次文档变更。
- **输入规则**：行内（`**粗体**`）与块级（`## `）两类，都是观察事务流后发命令。
- **序列化**：HTML 与 markdown 的双向转换；粘贴时把外部 HTML 规整到 schema。
- **UI**：浮动工具栏、斜杠菜单、块拖拽——弹层与命中测试在 M6 已 Adopt。

## 9. 出口门禁

沿用 `m10-capability-decisions.md` 的六项：

| 要求             | 口径                                                                             |
| ---------------- | -------------------------------------------------------------------------------- |
| 真实业务 fixture | 一份真实文档录制（≥5,000 块、混合 mark 密度、含嵌套列表与行内原子）              |
| 性能与包体上限   | 帧时按 `design.md` §2.1；WASM 增量在 M9 余量内单独归因；编辑延迟不随文档长度增长 |
| API/ABI diff     | ABI 版本递增 + golden 字节 + 跨语言 round trip + 畸形输入 + fuzz                 |
| oracle           | 单 run 逐字节不变；多 run 对多节点朴素实现像素一致；映射的往返属性测试           |
| 平台资格         | 真实 IME 在 mark 边界与块边界的组合录制                                          |
| kill switch      | `richTextEnabled` 关闭后回到单 run 单会话，文档降级为纯文本                      |

## 10. 风险

| 风险                       | 判据                                | 处置                            |
| -------------------------- | ----------------------------------- | ------------------------------- |
| 分段 shaping 破坏连字      | 与单 run 输出在同字体同字号下不一致 | run 边界不切断 shaping cluster  |
| 结构往返出现 caret 闪帧    | 回车后 caret 位置在两帧间跳变       | 乐观预演；不达标则 P4 不合入    |
| 乐观预演与 schema 结果分歧 | 校正后的文档与 Shell 的结果不同     | 以 Shell 为准，且分歧计数进诊断 |
| 投影每帧全量传输拖垮长文档 | 编辑延迟随块数增长                  | 投影按 revision 增量传输        |
| 多 run 打崩文本缓存        | 缓存命中率门禁下降                  | 按 run 而非按节点缓存           |
| WASM 体积吃掉 M9 余量      | 归因超出门禁                        | 富文本作为可选模块              |

## 11. 仍然排除

- **协同编辑与 CRDT**：本设计的映射是协同的前提，但所有权与冲突解决是另一套问题。
- **表格**：跨单元格选区是第四种选区，单独立项。
- **公式与第三方插件体系**。

## 12. 已定案（原「未决」）

1. **投影的传输形式**：Shell 在 `ConfigureDocument` 上**全量声明**块序列——每块一个稳定
   key、持有其文本的 Scene 节点（未物化时为 `NULL_NODE_ID`）、UTF-16 长度、是否原子。
   不走增量：这条指令只在块的**结构**变化时发（回车、合并、粘贴），不随按键发，而
   §9 的性能门禁量的正是「编辑延迟不随文档长度增长」，5,000 块实测 0.92 倍（见
   `pnpm e15:perf`）。若将来结构编辑本身成为热点，增量传输是下一步，不是现在的。

   P3 最初的定案是「Scene 就是投影」（Core 走一遍树）。P5 推翻了它：虚拟化下未物化的
   块**根本没有节点**，走树只能得到屏幕上那几十块。声明式列表是唯一能同时表达两者的
   形式。

2. **undo 与结构往返的交互**：**一步**。结构请求不进 undo 栈——Shell 收到请求后产出的
   新投影是一次普通的 Shell 变更，而 Core 侧的文本改动（分裂前删掉选区、合并后的文本）
   走的是既有的 undo 分组规则：一次 `Replace` 从不并入输入突发（P0），所以一次结构编辑
   在栈上就是它自己那一步。

3. **块虚拟化下的选区**：Core 的位置空间持有**每块的长度**，只持有**已物化块的文本**。
   长度是扁平空间和跨块选区需要的，每块一个整数；文本是 grapheme 安全的移动和部分删除
   需要的，而只有用户看得见的块才需要那些。5,000 块文档因此在 Core 里是每个屏外块一个
   整数，不是文档的第二份拷贝。

   未物化块占据它声明的那些位置：选区能跨过它，删除能整块删掉它而文本从未到达。它唯一
   做不到的是持有 caret——方向键停在它旁边的 gap 上，Core 发出物化请求，把「caret 不动」
   变成「延迟一帧」。落在它内部的选区端点夹到边界（边界总是合法的），而不是发明一个
   Core 无法校验的 grapheme 边界。

**富文本是可选模块。** 编译进来要 18,390 gzip bytes，超出 M9 工程门禁，所以 §10 风险表
写好的处置「富文本作为可选模块」照做：`pingo-core` 的 `rich-text` feature 默认开启
（`cargo test` 测的是完整能力），而默认发布产物不含它，落在 389,313，工程门禁下余
3,903 bytes。`PINGO_RICH_TEXT=1 pnpm core:wasm` 写出含它的产物，按 400 KiB 产品上限
把关——工程余量正是这个模块要花的——落在 **407,703，产品上限下余 1,897 bytes**。
归因与回收过程见 [`wasm-size-attribution.md`](wasm-size-attribution.md)。

**没有做的：** §7 列的浮动工具栏、斜杠菜单、块拖拽。它们是 UI 面，不在 §1 的十一条验收
里，也不阻塞任何一刀的出口；`@dopejs/pingo-editor` 给了它们要用的全部命令与查询
（`toggleMark`、`markIsActive`、`setBlockType`、`splitBlock`），弹层与命中测试在 M6
已 Adopt。

## 14. 本文不做的事

不实现任何一刀；不写 `@dopejs/pingo-editor` 的 API 签名；不为第 11 节预留接口。本文确定
