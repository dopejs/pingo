# 아키텍처 개요

## 양측 소유권

```
TSX / hooks          →  Mutation Stream  →   Scene / Layout / Paint
（TypeScript Shell）       이진, 배치          （Rust Core, wasm）
                                                    ↓
Canvas2D 재생기      ←   DisplayList      ←    Picture
```

**Shell은 컴포넌트 트리를 소유하고, Core는 Scene을 소유합니다. 양측은 가변 객체를 공유하지 않습니다.**
모든 경계 간 통신은 버전이 지정된 이진 스트림입니다. 리틀 엔디언, 4바이트 정렬, 명령어 기반으로,
수신 측은 메모리에 접근하기 전에 opcode, 길이, 정렬, ID, 산술 검증을 완료하며, 잘못된 입력은
부분 적용되지 않고 원자적으로 거부됩니다.

이 경계는 성능 최적화가 아니라 정확성 경계입니다. 바이트가 일반적으로 이 프로젝트 자체 인코더에서
나온다 하더라도, 디코더는 신뢰할 수 없는 입력으로 취급하며 fuzz 테스트로 커버합니다.

## 이중 클록

UI 클록(메인 스레드)과 렌더링 클록(Worker)은 서로 독립적입니다.

- 메인 스레드는 입력을 수집하고, 컴포넌트 트리를 실행하고, Mutation 프레임을 커밋합니다.
- Worker는 스크롤 물리, 애니메이션, 레이아웃, 합성을 구동합니다.

**스크롤 안정 상태에서는 Shell을 호출하지 않습니다.** 누락된 데이터는 플레이스홀더로 렌더링하고,
이후 프레임에서 보충 생성합니다. 따라서 메인 스레드가 비즈니스 코드에 의해 200ms간 차단되어도
스크롤과 애니메이션은 계속 연속적으로 동작합니다. 이 시나리오는 자동 장애 주입 테스트로 보호됩니다.

## 폴백 체인

기능 감지가 순서대로 전송 경로를 선택하며, 세 단계는 기능적으로 동등합니다.

1. **SharedArrayBuffer** —— 교차 출처 격리(COOP/COEP) 필요
2. **postMessage** —— SAB가 없을 때
3. **메인 스레드 Canvas2D** —— Worker/OffscreenCanvas가 없을 때

```ts
const root = await createHostedCanvasRoot(canvas, {
  transport: { preference: "sab" }, // 선택적 선호, 충족되지 않으면 여전히 폴백함
});
console.log(root.mode); // "sab" | "post-message" | "main-thread"
```

이 사이트의 [Playground](/playground)가 살아 있는 예입니다. GitHub Pages는 COOP/COEP 응답 헤더를
내려줄 수 없으므로 온라인에서는 postMessage 경로로 실행되며, 페이지 상단의 transport 표시가
이를如实하게 보여줍니다.

## 무효화 모델

**prop 의미론이 무효화 영역을 결정합니다.** 호출 측은 수동으로 더티 표시를 하지 않으며,
`forceUpdate` 탈출구도 없습니다.

각 속성은 단일 소스 스키마에서 레이아웃, 페인트, 히트, 의미 중 무엇에 영향을 주는지 선언합니다.
`opacity`를 변경해도 리플로가 발생하지 않으며, `width`를 변경하면 발생합니다. 더티 비트맵은 영역별로
유지 관리되며, `onFrame`은 각 영역의 더티 노드 수를 노출합니다.

이 선택은 "공격적 최소 무효화 + 속성 테스트 백스톱"입니다. 증분 렌더링 결과는 전체 렌더링과
픽셀 단위로 일치해야 하며, 차이 테스트는 반례를 최소 실패 케이스로 수렴시킵니다.

## Scene 표현

Core 내부의 Scene은 SoA(구조체 배열을 배열의 구조체로 변환)입니다.

- 노드 ID는 **세대**를 포함하여, 슬롯 재사용으로 인해 만료된 ID가 다시 유효해지지 않습니다.
- 커밋 후 **위상 정렬**을 유지합니다. 부모 노드는 항상 자식 노드보다 앞에 위치합니다.
- 구조 편집은 매 커밋마다 한 번씩 압축하며, 매 mutation마다 하지 않습니다.
- 레이아웃 결과는 이중 버퍼 SoA로 일괄 비교하며, 핫 경로에서는 노드별 클로저나 리스너 할당이 없습니다.

## 백엔드 플러그형

Core는 플랫한 이진 DisplayList를 출력하며, 백엔드는 단순한 재생기입니다. Canvas2D 백엔드는
인색하게 할당하는 typed-array 루프입니다. **매 그리기마다 wasm→JS를 호출하는 것은 수용 가능한
렌더링 경로가 아닙니다.**

동일한 DisplayList는 격리된 wgpu 프로토타입에도 공급되며, 양쪽 출력은 픽셀 차이 검사를 수행합니다.
WebGPU 채택 여부는 데이터 기반 결정이며, [ADR-0006](/adr/0006-webgpu-backend-decision)을 참조하십시오.

## 결정성

시간, 난수 소스, 입력 스트림은 주입 또는 재생이 가능하며, Core 출력은 스레드 스케줄링 순서에
의존하지 않습니다. `DOPR` 아카이브는 Mutation과 Input 스트림을 원래 순서대로 기록하며, 브라우저에서
벗어나 headless 환경에서 결정적으로 재생할 수 있습니다. 따라서 온라인 문제를 로컬에서 재현할 수
있으며, 민감한 편집 스트림은 명시적으로 기록을 건너뜁니다.

## 컴포넌트와 스타일

이 커널 위에는 세 계층의 작성자 대상 API가 있습니다.

- **기본 컴포넌트** —— View/Text/Image, Input/TextArea, SVG/Path 등 엔진 수준 요소,
  [기본 컴포넌트](/guide/elements)를 참조하십시오.
- **스타일** —— Shell 측에서 파싱하는 버전이 지정된 CSS 서브셋(지원 표는 [여기](/style-support) 참조)과
  빌드 시점의 [SCSS/Less 파이프라인](/guide/scss-less), Core는 정규화된 타입 값만 소비하며
  CSS 텍스트를 파싱하지 않습니다.
- **UI 컴포넌트 라이브러리** —— `@dopejs/pingo-ui`, shadcn/ui와 정렬된 완성 컴포넌트로,
  모두 canvas에 렌더링됩니다. [컴포넌트 문서](/components)를 참조하십시오.
